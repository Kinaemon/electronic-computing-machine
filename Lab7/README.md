# Лабораторная работа 7. Обращение матрицы

## Как проверить решение?

Программа приближает обратную матрицу суммой `X = (I + R + … + R^(M-1)) B`, где `B = Aᵀ / (‖A‖₁ · ‖A‖∞)` и `R = I − BA`. В точной арифметике `AX = I − (I − AB)^M`. Для обратимой `A` невязка стремится к нулю с ростом `M`. В вычислениях с `float` к ошибке усечения ряда добавляется округление.

Проверка вычисляет `‖AX − I‖∞` — максимальную сумму модулей элементов по строкам. Команда `make check` требует невязку не больше `1e-4` во всех четырёх программах для двух матриц.

- Несимметричная `3×3` проверяет в том числе транспонирование при построении `B`.
- Сгенерированная `27×27` задействует цикл по 16 элементов, дополнительный AVX-шаг по 8 элементов и скалярный хвост.

Невязки на этих тестах получились порядка `1e-6`. Программа вычисляет и выводит невязку при любом размере матрицы, включая `N = 2048` в `make bench`. Время в строке `Time` измеряется до вычисления невязки. Порог `1e-4` относится к матрицам и числу членов ряда в `make check`.

## Почему ускорение меньше восьми раз?

В 256-битный вектор помещается восемь чисел `float` по 32 бита. Это ширина одной векторной операции. Время даже полностью векторизованного цикла зависит и от других факторов. [Справочник Intel по intrinsics](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html)

- **Доступ к данным.** На каждый вектор `matmul_simd` читает элементы `B` и `C`, выполняет FMA и записывает обновлённый `C`. Пропускная способность загрузки и записи ограничивает число таких обновлений в секунду.
- **Кэш.** При порядке циклов `i → k → j` для каждой строки результата заново читается вся матрица `B`. При `N = 2048` это 16 МиБ, больше кэша L2 одного ядра в проведённом замере. OpenBLAS использует блочное умножение, чтобы чаще повторно использовать данные из кэша. [Руководство разработчика OpenBLAS](https://github.com/OpenMathLib/OpenBLAS/blob/develop/docs/developers.md)
- **Зависимость по `k`.** Каждый проход по `k` обновляет уже накопленное значение `C[i][j]`. SIMD параллельно обрабатывает разные `j`, а для каждого отдельного `j` следующему обновлению всё ещё нужен результат предыдущего.

При `N = 2048` скалярного хвоста в умножении нет, поскольку размер кратен 16.

## Какие варианты сравниваются?

| Программа | Как выполняются операции над матрицами |
| --- | --- |
| `inv_scalar` | Обычные циклы из `main_scalar.c`, автовекторизация выключена (`-fno-tree-vectorize`). |
| `inv_auto` | Те же циклы из `main_scalar.c`. GCC может векторизовать их с `-O3 -mavx2 -mfma -ftree-vectorize`. |
| `inv_simd` | Отдельный файл `main_simd.c` с ручными AVX-инструкциями через intrinsics, включая `_mm256_fmadd_ps`. |
| `inv_blas` | Умножение и сложение выполняет OpenBLAS. |

Отчёт GCC подтвердил, что в Auto внутренний цикл умножения использует 32-байтные векторы. В изученной сборке GCC сгенерировал для этого цикла `vmulps` и `vaddps`. В ручной версии умножение и сложение объединены в FMA. У Scalar сохранены исходные флаги сборки, поэтому в сравнении с ним учитывается и выбор инструкций процессора. [Опции оптимизации GCC](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html) · [Отчёты об оптимизациях GCC](https://gcc.gnu.org/onlinedocs/gcc/Developer-Options.html)

```sh
gcc -std=c11 -O3 -mavx2 -mfma -ftree-vectorize -fopt-info-vec-optimized -S main_scalar.c -o /dev/null
```

## Результат замера

Один запуск `make bench` на Intel Core i7-13700H с GCC 16.2.1. Все варианты считали при `N = 2048`, `M = 10`, OpenBLAS работал в один поток. Ускорение считается как время Scalar, делённое на время выбранного варианта.

| Вариант | Время, с | Ускорение | Невязка |
| --- | ---: | ---: | ---: |
| Scalar | 43,0888 | 1,00× | `5.522299e-03` |
| Auto | 14,2103 | 3,03× | `5.522299e-03` |
| SIMD | 14,8040 | 2,91× | `5.522314e-03` |
| BLAS | 2,9440 | 14,64× | `5.522594e-03` |

В этом замере Auto и ручной SIMD заняли примерно одинаковое время. OpenBLAS оказался примерно в 5 раз быстрее ручного SIMD.
